     1→     1→# PROJET : SYSTEMLAB
     2→     2→## Plateforme interactive d'apprentissage et de simulation du System Design
     3→     3→
     4→     4→Tu es un ingénieur logiciel senior spécialisé en Next.js, TypeScript,
     5→     5→architecture logicielle, systèmes distribués, simulation événementielle,
     6→     6→React Flow et conception d'interfaces techniques avancées.
     7→     7→
     8→     8→Ta mission est de développer une véritable application web appelée
     9→     9→SystemLab, en utilisant l'image jointe comme référence visuelle principale.
    10→    10→
    11→    11→ATTENTION :
    12→    12→L'image jointe est une maquette de référence. Elle définit l'apparence,
    13→    13→l'organisation générale et l'expérience utilisateur recherchées.
    14→    14→
    15→    15→Tu dois reproduire fidèlement son design, tout en construisant une
    16→    16→application fonctionnelle, interactive, maintenable et extensible.
    17→    17→
    18→    18→Ne te contente pas de reproduire l'image avec des composants statiques.
    19→    19→Les boutons, les panneaux, les connexions, les configurations et les
    20→    20→simulations doivent fonctionner.
    21→    21→
    22→    22→Ne remplace pas les fonctionnalités essentielles par de simples
    23→    23→animations ou des valeurs fictives.

    25→    25→==================================================
    26→    26→1. VISION DU PRODUIT
    27→    27→==================================================
    28→    28→
    29→    29→SystemLab est un laboratoire interactif destiné à apprendre le
    30→    30→System Design en construisant et en testant des architectures logicielles.
    31→    31→
    32→    32→L'utilisateur doit pouvoir :
    33→    33→
    34→    34→1. Construire une architecture visuellement.
    35→    35→2. Ajouter des composants informatiques.
    36→    36→3. Connecter les composants entre eux.
    37→    37→4. Configurer leurs propriétés.
    38→    38→5. Définir un scénario de trafic.
    39→    39→6. Lancer une simulation.
    40→    40→7. Observer les performances du système.
    41→    41→8. Identifier les goulots d'étranglement.
    42→    42→9. Simuler des pannes.
    43→    43→10. Comprendre les causes des problèmes.
    44→    44→11. Modifier l'architecture.
    45→    45→12. Comparer les résultats avant et après modification.
    46→    46→13. Apprendre les concepts techniques concernés.
    47→    47→
    48→    48→L'expérience doit être intuitive pour un débutant tout en permettant
    49→    49→aux utilisateurs avancés d'explorer des architectures complexes.
    50→    50→
    51→    51→Le produit doit ressembler à un outil d'ingénierie professionnel,
    52→    52→et non à un simple site de cours.
    53→    53→
    54→    54→INSPIRATIONS :
    55→    55→- n8n pour l'édition visuelle et les connexions.
    56→    56→- React Flow pour le canvas interactif.
    57→    57→- Linear pour la sobriété de l'interface.
    58→    58→- Grafana pour les tableaux de bord techniques.
    59→    59→- Figma pour la manipulation fluide des éléments.
    60→    60→
    61→    61→Ne copie pas exactement ces produits.
    62→    62→Crée une identité propre à SystemLab.
    63→    63→
    64→    64→Langue principale : français.
    65→    65→Les noms techniques reconnus peuvent rester en anglais.

   229→   229→6. ÉDITEUR VISUEL
   230→   230→==================================================
   231→   231→
   232→   232→C'est le cœur de SystemLab.
   233→   233→
   234→   234→L'utilisateur doit pouvoir construire une architecture sans écrire
   235→   235→de code.
   236→   236→
   237→   237→Utilise React Flow pour gérer le canvas.
   238→   238→
   239→   239→Fonctionnalités obligatoires :
   240→   240→
   241→   241→- Ajouter un composant par glisser-déposer.
   242→   242→- Déplacer les composants.
   243→   243→- Sélectionner un composant.
   244→   244→- Sélectionner plusieurs composants.
   245→   245→- Relier les composants.
   246→   246→- Déplacer les connexions.
   247→   247→- Supprimer une connexion.
   248→   248→- Supprimer un composant.
   249→   249→- Dupliquer un composant.
   250→   250→- Copier et coller.
   251→   251→- Annuler une modification.
   252→   252→- Rétablir une modification.
   253→   253→- Zoom avant et arrière.
   254→   254→- Déplacer la vue.
   255→   255→- Ajuster la vue à l'écran.
   256→   256→- Afficher une minimap.
   257→   257→- Sélectionner une zone.
   258→   258→- Ajouter des notes.
   259→   259→- Créer des groupes visuels.
   260→   260→- Renommer l'architecture.
   261→   261→- Sauvegarder les modifications.
   262→   262→- Charger une architecture existante.
   263→   263→
   264→   264→Prévoir un système de validation des connexions.
   265→   265→
   266→   266→Exemple :
   267→   267→Une connexion entre un client HTTP et un serveur API est valide.
   268→   268→
   269→   269→Une connexion incompatible doit afficher un message explicatif
   270→   270→sans bloquer toute l'application.
   271→   271→
   272→   272→Les connexions doivent posséder :
   273→   273→- Une source.
   274→   274→- Une destination.
   275→   275→- Un type.
   276→   276→- Un protocole éventuel.
   277→   277→- Des paramètres réseau.
   278→   278→- Un sens de circulation.
   279→   279→- Des métriques de simulation.
   280→   280→
   281→   281→L'utilisateur doit pouvoir sélectionner une connexion pour modifier
   282→   282→ses propriétés.
   283→   283→
   284→   284→Les groupes visuels doivent permettre de regrouper des composants
   285→   285→par domaine, région ou couche architecturale.
   286→   286→
   287→   287→Ne confonds pas un groupe visuel avec un composant exécutant un
   288→   288→traitement.

   550→   550→

   552→   552→ou indique clairement qu'il s'agit d'estimations initiales.
   553→   553→
   554→   554→Exemple de configuration d'un serveur API :
   555→   555→
   556→   556→- Nombre d'instances.
   557→   557→- Capacité par instance.
   558→   558→- Temps de traitement moyen.
   559→   559→- Variabilité du temps de traitement.
   560→   560→- CPU disponible.
   561→   561→- Mémoire disponible.
   562→   562→- Nombre maximal de requêtes concurrentes.
   563→   563→- Nombre maximal de connexions.
   564→   564→- Politique de répartition.
   565→   565→- Taux d'erreur éventuel.
   566→   566→
   567→   567→Exemple de configuration PostgreSQL :
   568→   568→
   569→   569→- Capacité de traitement.
   570→   570→- Temps de service moyen.
   571→   571→- Nombre de connexions maximum.
   572→   572→- Taille des données.
   573→   573→- Proportion de lectures.
   574→   574→- Proportion d'écritures.
   575→   575→- Index.
   576→   576→- Cache.
   577→   577→- Réplication.
   578→   578→- Nombre de réplicas.
   579→   579→- Politique de réplication.
   580→   580→- CPU.
   581→   581→- Mémoire.
   582→   582→
   583→   583→Utilise des formulaires validés et des paramètres adaptés à chaque
   584→   584→composant.
   585→   585→
   586→   586→Les valeurs doivent être modifiables et leur signification expliquée.
   587→   587→
   588→   588→==================================================
   589→   589→9. ARCHITECTURE DU MOTEUR DE SIMULATION
   590→   590→==================================================
   591→   591→
   592→   592→C'est la partie technique la plus importante.
   593→   593→
   594→   594→Construis un moteur hybride combinant :
   595→   595→
   596→   596→A. Calculs mathématiques.
   597→   597→B. Simulation événementielle.
   598→   598→
   599→   599→Sépare le moteur de simulation du code React.
   600→   600→
   601→   601→Le moteur doit pouvoir être testé indépendamment de l'interface.
   602→   602→
   603→   603→Ne mets pas la logique de calcul directement dans les composants UI.
   604→   604→
   605→   605→Architecture logique suggérée :
   606→   606→
   607→   607→src/
   608→   608→  app/
   609→   609→  components/
   610→   610→    editor/
   611→   611→    nodes/
   612→   612→    panels/
   613→   613→    simulation/
   614→   614→    charts/
   615→   615→    ui/
   616→   616→  features/
   617→   617→    architectures/
   618→   618→    components-library/
   619→   619→    simulations/
   620→   620→    learning/
   621→   621→  engine/
   622→   622→    graph/
   623→   623→    math/
   624→   624→    events/
   625→   625→    queueing/
   626→   626→    failures/
   627→   627→    metrics/
   628→   628→    diagnostics/
   629→   629→  lib/
   630→   630→    validation/
   631→   631→    persistence/
   632→   632→  stores/
   633→   633→  types/
   634→   634→  tests/
   635→   635→
   636→   636→Adapte cette structure à celle du projet existant.
   637→   637→
   638→   638→A. MOTEUR MATHÉMATIQUE
   639→   639→
   640→   640→Utiliser des calculs déterministes pour estimer :
   641→   641→- Capacités.
   642→   642→- Débits.
   643→   643→- Utilisation des ressources.
   644→   644→- Latences.
   645→   645→- Files d'attente simplifiées.
   646→   646→- Limites de concurrence.
   647→   647→- Coûts estimés.
   648→   648→- Propagation des goulots d'étranglement.
   649→   649→
   650→   650→B. MOTEUR ÉVÉNEMENTIEL
   651→   651→
   652→   652→Simuler :
   653→   653→- Arrivée des requêtes.
   654→   654→- Déplacement des requêtes dans le graphe.
   655→   655→- Traitement par les composants.
   656→   656→- Files d'attente.
   657→   657→- Délais de traitement.
   658→   658→- Délais réseau.
   659→   659→- Concurrence.
   660→   660→- Saturation.
   661→   661→- Erreurs.
   662→   662→- Timeouts.
   663→   663→- Pannes.
   664→   664→- Reprise des services.
   665→   665→- Retry.
   666→   666→- Circuit Breaker.
   667→   667→- Événements asynchrones.
   668→   668→
   669→   669→Utilise une horloge virtuelle et une file d'événements ordonnée
   670→   670→par temps de simulation.
   671→   671→
   672→   672→Ne simule pas chaque requête individuelle lorsque le volume rend
   673→   673→cette approche trop coûteuse.
   674→   674→
   675→   675→Prévois plusieurs niveaux de précision :
   676→   676→
   677→   677→1. Estimation analytique rapide.
   678→   678→2. Simulation événementielle avec échantillonnage.
   679→   679→3. Simulation détaillée pour les scénarios compatibles.
   680→   680→
   681→   681→Les résultats doivent préciser le mode utilisé.
   682→   682→
   683→   683→C. PROPAGATION DES REQUÊTES
   684→   684→
   685→   685→Une requête doit pouvoir traverser plusieurs composants.
   686→   686→
   687→   687→Exemple :
   688→   688→
   689→   689→Clients
   690→   690→  -> Load Balancer
   691→   691→  -> API Servers
   692→   692→  -> Redis
   693→   693→  -> PostgreSQL
   694→   694→
   695→   695→Le moteur doit :
   696→   696→- Respecter les connexions du graphe.
   697→   697→- Calculer les délais de traitement.
   698→   698→- Tenir compte des capacités.
   699→   699→- Simuler les files d'attente.
   700→   700→- Propager les erreurs.
   701→   701→- Calculer les métriques de bout en bout.
   702→   702→
   703→   703→Le moteur doit détecter les cycles dans le graphe.
   704→   704→
   705→   705→Les cycles ne doivent pas provoquer de boucle infinie.
   706→   706→
   707→   707→Une architecture invalide doit recevoir un diagnostic compréhensible.
   708→   708→
   709→   709→D. FILES D'ATTENTE
   710→   710→
   711→   711→Modéliser au minimum :
   712→   712→- Capacité de service.
   713→   713→- Nombre de workers.
   714→   714→- Temps de service.
   715→   715→- Nombre de requêtes en attente.
   716→   716→- Saturation.
   717→   717→- Temps d'attente.
   718→   718→- Rejets lorsque les limites sont atteintes.
   719→   719→
   720→   720→Évite les formules simplistes lorsque leurs hypothèses ne sont
   721→   721→pas satisfaites.
   722→   722→
   723→   723→Par exemple, une approximation de file d'attente ne doit pas être
   724→   724→présentée comme fiable lorsque le système est instable.
   725→   725→
   726→   726→E. LATENCE
   727→   727→
   728→   728→Distinguer :
   729→   729→- Latence réseau.
   730→   730→- Temps de traitement.
   731→   731→- Temps d'attente.
   732→   732→- Latence totale.
   733→   733→- Moyenne.
   734→   734→- p50.
   735→   735→- p95.
   736→   736→- p99.
   737→   737→
   738→   738→Les percentiles doivent être calculés à partir de données simulées
   739→   739→appropriées ou d'une approximation explicitement documentée.
   740→   740→
   741→   741→Ne calcule pas le p95 en multipliant arbitrairement la moyenne.
   742→   742→
   743→   743→F. CAPACITÉ ET SATURATION
   744→   744→
   745→   745→Calculer les limites en fonction des paramètres du composant.
   746→   746→
   747→   747→Une saturation doit avoir des conséquences cohérentes :
   748→   748→- Augmentation de la file d'attente.
   749→   749→- Augmentation de la latence.
   750→   750→- Rejets.
   751→   751→- Timeouts.
   752→   752→- Propagation de la surcharge.
   753→   753→
   754→   754→G. RÉPPLICATION ET CACHE
   755→   755→
   756→   756→Implémenter progressivement les modèles de :
   757→   757→- Cache hit et cache miss.
   758→   758→- Politiques de cache.
   759→   759→- Réplication en lecture.
   760→   760→- Réplication en écriture.
   761→   761→- Latence de réplication.
   762→   762→- Capacité des réplicas.
   763→   763→
   764→   764→Documenter les hypothèses de chaque modèle.
   765→   765→
   766→   766→H. PANNES
   767→   767→
   768→   768→Permettre de configurer :
   769→   769→- Début de la panne.
   770→   770→- Durée.
   771→   771→- Composant concerné.
   772→   772→- Indisponibilité complète ou dégradation.
   773→   773→- Temps de récupération.
   774→   774→
   775→   775→Observer les conséquences sur les composants dépendants.
   776→   776→
   777→   777→I. REPRODUCTIBILITÉ
   778→   778→
   779→   779→Permettre de configurer une seed aléatoire.
   780→   780→
   781→   781→À paramètres et seed identiques, les résultats doivent être
   782→   782→reproductibles autant que possible.
   783→   783→
   784→   784→J. MÉTRIQUES
   785→   785→
   786→   786→Produire :
   787→   787→- Débit entrant.
   788→   788→- Débit traité.
   789→   789→- Latence.
   790→   790→- Erreurs.
   791→   791→- Rejets.
   792→   792→- CPU estimé.
   793→   793→- Mémoire estimée.
   794→   794→- Longueur des files.
   795→   795→- Temps d'attente.
   796→   796→- Disponibilité simulée.
   797→   797→- Coût estimé.
   798→   798→
   799→   799→Chaque métrique doit avoir une définition claire.
   800→   800→
   801→   801→Ne mélange pas les unités.
   802→   802→

   807→   807→Créer une interface de configuration du trafic.

   809→   809→Paramètres :

   815→   815→- Proportion lecture/écriture.
   816→   816→- Latence réseau.
   817→   817→- Taux d'erreur initial.
   818→   818→- Profil de trafic.
   819→   819→- Seed aléatoire.
   820→   820→- Budget cible.
   821→   821→
   822→   822→Profils :
   823→   823→- Constant.
   824→   824→- Progressif.
   825→   825→- Pic soudain.
   826→   826→- En vagues.
   827→   827→- Aléatoire.
   828→   828→- Personnalisé.
   829→   829→
   830→   830→Modes :
   831→   831→- Test rapide.
   832→   832→- Test de charge.
   833→   833→- Test de stress.
   834→   834→- Test d'endurance.

   848→   848→Afficher une progression et permettre d'interrompre le calcul.

   851→   851→11. DIAGNOSTICS INTELLIGENTS
   852→   852→==================================================
   853→   853→
   854→   854→Créer un moteur de diagnostic basé sur des règles explicites
   855→   855→et sur les métriques produites par le simulateur.
   856→   856→
   857→   857→Ne rends pas l'utilisation d'une API d'IA obligatoire pour
   858→   858→obtenir des diagnostics corrects.
   859→   859→
   860→   860→Exemples de règles :
   861→   861→
   862→   862→- Saturation d'un composant.
   863→   863→- File d'attente qui augmente.
   864→   864→- Dépendance critique sans redondance.
   865→   865→- Base de données trop sollicitée.
   866→   866→- Cache peu efficace.
   867→   867→- Trop de connexions concurrentes.
   868→   868→- Risque de cascade de timeouts.
   869→   869→- Composant isolé.
   870→   870→- Connexion invalide.
   871→   871→- Architecture impossible à simuler correctement.
   872→   872→
   873→   873→Chaque diagnostic contient :
   874→   874→
   875→   875→- Gravité.
   876→   876→- Composant concerné.
   877→   877→- Métriques justificatives.
   878→   878→- Cause probable.
   879→   879→- Explication pédagogique.
   880→   880→- Solutions possibles.
   881→   881→- Compromis.
   882→   882→- Limites de la recommandation.
   883→   883→
   884→   884→Exemple :
   885→   885→
   886→   886→"PostgreSQL devient le principal goulot d'étranglement."
   887→   887→
   888→   888→Afficher les métriques qui justifient cette conclusion.
   889→   889→
   890→   890→Puis proposer plusieurs pistes :
   891→   891→- Optimiser les requêtes.
   892→   892→- Ajouter un cache.
   893→   893→- Augmenter la capacité.
   894→   894→- Introduire des réplicas de lecture.
   895→   895→
   896→   896→Préciser les conditions dans lesquelles chaque solution est utile.
   897→   897→
   898→   898→Ne recommande pas automatiquement un réplica de lecture pour
   899→   899→résoudre une surcharge principalement liée aux écritures.
   900→   900→
