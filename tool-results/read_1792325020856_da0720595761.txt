     1→# PROJET : SYSTEMLAB
     2→## Plateforme interactive d'apprentissage et de simulation du System Design
     3→
     4→Tu es un ingénieur logiciel senior spécialisé en Next.js, TypeScript,
     5→architecture logicielle, systèmes distribués, simulation événementielle,
     6→React Flow et conception d'interfaces techniques avancées.
     7→
     8→Ta mission est de développer une véritable application web appelée
     9→SystemLab, en utilisant l'image jointe comme référence visuelle principale.
    10→
    11→ATTENTION :
    12→L'image jointe est une maquette de référence. Elle définit l'apparence,
    13→l'organisation générale et l'expérience utilisateur recherchées.
    14→
    15→Tu dois reproduire fidèlement son design, tout en construisant une
    16→application fonctionnelle, interactive, maintenable et extensible.
    17→
    18→Ne te contente pas de reproduire l'image avec des composants statiques.
    19→Les boutons, les panneaux, les connexions, les configurations et les
    20→simulations doivent fonctionner.
    21→
    22→Ne remplace pas les fonctionnalités essentielles par de simples
    23→animations ou des valeurs fictives.
    24→
    25→==================================================
    26→1. VISION DU PRODUIT
    27→==================================================
    28→
    29→SystemLab est un laboratoire interactif destiné à apprendre le
    30→System Design en construisant et en testant des architectures logicielles.
    31→
    32→L'utilisateur doit pouvoir :
    33→
    34→1. Construire une architecture visuellement.
    35→2. Ajouter des composants informatiques.
    36→3. Connecter les composants entre eux.
    37→4. Configurer leurs propriétés.
    38→5. Définir un scénario de trafic.
    39→6. Lancer une simulation.
    40→7. Observer les performances du système.
    41→8. Identifier les goulots d'étranglement.
    42→9. Simuler des pannes.
    43→10. Comprendre les causes des problèmes.
    44→11. Modifier l'architecture.
    45→12. Comparer les résultats avant et après modification.
    46→13. Apprendre les concepts techniques concernés.
    47→
    48→L'expérience doit être intuitive pour un débutant tout en permettant
    49→aux utilisateurs avancés d'explorer des architectures complexes.
    50→
    51→Le produit doit ressembler à un outil d'ingénierie professionnel,
    52→et non à un simple site de cours.
    53→
    54→INSPIRATIONS :
    55→- n8n pour l'édition visuelle et les connexions.
    56→- React Flow pour le canvas interactif.
    57→- Linear pour la sobriété de l'interface.
    58→- Grafana pour les tableaux de bord techniques.
    59→- Figma pour la manipulation fluide des éléments.
    60→
    61→Ne copie pas exactement ces produits.
    62→Crée une identité propre à SystemLab.
    63→
    64→Langue principale : français.
    65→Les noms techniques reconnus peuvent rester en anglais.

   229→6. ÉDITEUR VISUEL
   230→==================================================
   231→
   232→C'est le cœur de SystemLab.
   233→
   234→L'utilisateur doit pouvoir construire une architecture sans écrire
   235→de code.
   236→
   237→Utilise React Flow pour gérer le canvas.
   238→
   239→Fonctionnalités obligatoires :
   240→
   241→- Ajouter un composant par glisser-déposer.
   242→- Déplacer les composants.
   243→- Sélectionner un composant.
   244→- Sélectionner plusieurs composants.
   245→- Relier les composants.
   246→- Déplacer les connexions.
   247→- Supprimer une connexion.
   248→- Supprimer un composant.
   249→- Dupliquer un composant.
   250→- Copier et coller.
   251→- Annuler une modification.
   252→- Rétablir une modification.
   253→- Zoom avant et arrière.
   254→- Déplacer la vue.
   255→- Ajuster la vue à l'écran.
   256→- Afficher une minimap.
   257→- Sélectionner une zone.
   258→- Ajouter des notes.
   259→- Créer des groupes visuels.
   260→- Renommer l'architecture.
   261→- Sauvegarder les modifications.
   262→- Charger une architecture existante.
   263→
   264→Prévoir un système de validation des connexions.
   265→
   266→Exemple :
   267→Une connexion entre un client HTTP et un serveur API est valide.
   268→
   269→Une connexion incompatible doit afficher un message explicatif
   270→sans bloquer toute l'application.
   271→
   272→Les connexions doivent posséder :
   273→- Une source.
   274→- Une destination.
   275→- Un type.
   276→- Un protocole éventuel.
   277→- Des paramètres réseau.
   278→- Un sens de circulation.
   279→- Des métriques de simulation.
   280→
   281→L'utilisateur doit pouvoir sélectionner une connexion pour modifier
   282→ses propriétés.
   283→
   284→Les groupes visuels doivent permettre de regrouper des composants
   285→par domaine, région ou couche architecturale.
   286→
   287→Ne confonds pas un groupe visuel avec un composant exécutant un
   288→traitement.

   589→9. ARCHITECTURE DU MOTEUR DE SIMULATION
   590→==================================================
   591→
   592→C'est la partie technique la plus importante.
   593→
   594→Construis un moteur hybride combinant :
   595→
   596→A. Calculs mathématiques.
   597→B. Simulation événementielle.
   598→
   599→Sépare le moteur de simulation du code React.
   600→
   601→Le moteur doit pouvoir être testé indépendamment de l'interface.
   602→
   603→Ne mets pas la logique de calcul directement dans les composants UI.
   604→
   605→Architecture logique suggérée :
   606→
   607→src/
   608→  app/
   609→  components/
   610→    editor/
   611→    nodes/
   612→    panels/
   613→    simulation/
   614→    charts/
   615→    ui/
   616→  features/
   617→    architectures/
   618→    components-library/
   619→    simulations/
   620→    learning/
   621→  engine/
   622→    graph/
   623→    math/
   624→    events/
   625→    queueing/
   626→    failures/
   627→    metrics/
   628→    diagnostics/
   629→  lib/
   630→    validation/
   631→    persistence/
   632→  stores/
   633→  types/
   634→  tests/
   635→
   636→Adapte cette structure à celle du projet existant.
   637→
   638→A. MOTEUR MATHÉMATIQUE
   639→
   640→Utiliser des calculs déterministes pour estimer :
   641→- Capacités.
   642→- Débits.
   643→- Utilisation des ressources.
   644→- Latences.
   645→- Files d'attente simplifiées.
   646→- Limites de concurrence.
   647→- Coûts estimés.
   648→- Propagation des goulots d'étranglement.
   649→
   650→B. MOTEUR ÉVÉNEMENTIEL
   651→
   652→Simuler :
   653→- Arrivée des requêtes.
   654→- Déplacement des requêtes dans le graphe.
   655→- Traitement par les composants.
   656→- Files d'attente.
   657→- Délais de traitement.
   658→- Délais réseau.
   659→- Concurrence.
   660→- Saturation.
   661→- Erreurs.
   662→- Timeouts.
   663→- Pannes.
   664→- Reprise des services.
   665→- Retry.
   666→- Circuit Breaker.
   667→- Événements asynchrones.
   668→
   669→Utilise une horloge virtuelle et une file d'événements ordonnée
   670→par temps de simulation.
   671→
   672→Ne simule pas chaque requête individuelle lorsque le volume rend
   673→cette approche trop coûteuse.
   674→
   675→Prévois plusieurs niveaux de précision :
   676→
   677→1. Estimation analytique rapide.
   678→2. Simulation événementielle avec échantillonnage.
   679→3. Simulation détaillée pour les scénarios compatibles.
   680→
   681→Les résultats doivent préciser le mode utilisé.
   682→
   683→C. PROPAGATION DES REQUÊTES
   684→
   685→Une requête doit pouvoir traverser plusieurs composants.
   686→
   687→Exemple :
   688→
   689→Clients
   690→  -> Load Balancer
   691→  -> API Servers
   692→  -> Redis
   693→  -> PostgreSQL
   694→
   695→Le moteur doit :
   696→- Respecter les connexions du graphe.
   697→- Calculer les délais de traitement.
   698→- Tenir compte des capacités.
   699→- Simuler les files d'attente.
   700→- Propager les erreurs.
   701→- Calculer les métriques de bout en bout.
   702→
   703→Le moteur doit détecter les cycles dans le graphe.
   704→
   705→Les cycles ne doivent pas provoquer de boucle infinie.
   706→
   707→Une architecture invalide doit recevoir un diagnostic compréhensible.
   708→
   709→D. FILES D'ATTENTE
   710→
   711→Modéliser au minimum :
   712→- Capacité de service.
   713→- Nombre de workers.
   714→- Temps de service.
   715→- Nombre de requêtes en attente.
   716→- Saturation.
   717→- Temps d'attente.
   718→- Rejets lorsque les limites sont atteintes.
   719→
   720→Évite les formules simplistes lorsque leurs hypothèses ne sont
   721→pas satisfaites.
   722→
   723→Par exemple, une approximation de file d'attente ne doit pas être
   724→présentée comme fiable lorsque le système est instable.
   725→
   726→E. LATENCE
   727→
   728→Distinguer :
   729→- Latence réseau.
   730→- Temps de traitement.
   731→- Temps d'attente.
   732→- Latence totale.
   733→- Moyenne.
   734→- p50.
   735→- p95.
   736→- p99.
   737→
   738→Les percentiles doivent être calculés à partir de données simulées
   739→appropriées ou d'une approximation explicitement documentée.
   740→
   741→Ne calcule pas le p95 en multipliant arbitrairement la moyenne.
   742→
   743→F. CAPACITÉ ET SATURATION
   744→
   745→Calculer les limites en fonction des paramètres du composant.
   746→
   747→Une saturation doit avoir des conséquences cohérentes :
   748→- Augmentation de la file d'attente.
   749→- Augmentation de la latence.
   750→- Rejets.
   751→- Timeouts.
   752→- Propagation de la surcharge.
   753→
   754→G. RÉPPLICATION ET CACHE
   755→
   756→Implémenter progressivement les modèles de :
   757→- Cache hit et cache miss.
   758→- Politiques de cache.
   759→- Réplication en lecture.
   760→- Réplication en écriture.
   761→- Latence de réplication.
   762→- Capacité des réplicas.
   763→
   764→Documenter les hypothèses de chaque modèle.
   765→
   766→H. PANNES
   767→
   768→Permettre de configurer :
   769→- Début de la panne.
   770→- Durée.
   771→- Composant concerné.
   772→- Indisponibilité complète ou dégradation.
   773→- Temps de récupération.
   774→
   775→Observer les conséquences sur les composants dépendants.
   776→
   777→I. REPRODUCTIBILITÉ
   778→
   779→Permettre de configurer une seed aléatoire.
   780→
   781→À paramètres et seed identiques, les résultats doivent être
   782→reproductibles autant que possible.
   783→

   785→

   787→- Débit entrant.
   788→- Débit traité.
   789→- Latence.

   791→- Rejets.

   793→- Mémoire estimée.
   794→- Longueur des files.
   795→- Temps d'attente.
   796→- Disponibilité simulée.
   797→- Coût estimé.
   798→
   799→Chaque métrique doit avoir une définition claire.
   800→
   801→Ne mélange pas les unités.

   851→11. DIAGNOSTICS INTELLIGENTS
   852→==================================================
   853→
   854→Créer un moteur de diagnostic basé sur des règles explicites
   855→et sur les métriques produites par le simulateur.
   856→

   861→
   862→- Saturation d'un composant.
   863→- File d'attente qui augmente.
   864→- Dépendance critique sans redondance.
   865→- Base de données trop sollicitée.
   866→- Cache peu efficace.
   867→- Trop de connexions concurrentes.
   868→- Risque de cascade de timeouts.
   869→- Composant isolé.
   870→- Connexion invalide.
   871→- Architecture impossible à simuler correctement.
   872→

   874→
   875→- Gravité.
   876→- Composant concerné.
   877→- Métriques justificatives.
   878→- Cause probable.
   879→- Explication pédagogique.
   880→- Solutions possibles.
   881→- Compromis.
   882→- Limites de la recommandation.
   883→
   884→Exemple :
   885→
   886→"PostgreSQL devient le principal goulot d'étranglement."
   887→
   888→Afficher les métriques qui justifient cette conclusion.
   889→
   890→Puis proposer plusieurs pistes :
   891→- Optimiser les requêtes.
   892→- Ajouter un cache.
   893→- Augmenter la capacité.
   894→- Introduire des réplicas de lecture.
   895→
   896→Préciser les conditions dans lesquelles chaque solution est utile.
   897→
   898→Ne recommande pas automatiquement un réplica de lecture pour
   899→résoudre une surcharge principalement liée aux écritures.
