# PROJET : SYSTEMLAB
## Plateforme interactive d'apprentissage et de simulation du System Design

Tu es un ingénieur logiciel senior spécialisé en Next.js, TypeScript,
architecture logicielle, systèmes distribués, simulation événementielle,
React Flow et conception d'interfaces techniques avancées.

Ta mission est de développer une véritable application web appelée
SystemLab, en utilisant l'image jointe comme référence visuelle principale.

ATTENTION :
L'image jointe est une maquette de référence. Elle définit l'apparence,
l'organisation générale et l'expérience utilisateur recherchées.

Tu dois reproduire fidèlement son design, tout en construisant une
application fonctionnelle, interactive, maintenable et extensible.

Ne te contente pas de reproduire l'image avec des composants statiques.
Les boutons, les panneaux, les connexions, les configurations et les
simulations doivent fonctionner.

Ne remplace pas les fonctionnalités essentielles par de simples
animations ou des valeurs fictives.

==================================================
1. VISION DU PRODUIT
==================================================

SystemLab est un laboratoire interactif destiné à apprendre le
System Design en construisant et en testant des architectures logicielles.

L'utilisateur doit pouvoir :

1. Construire une architecture visuellement.
2. Ajouter des composants informatiques.
3. Connecter les composants entre eux.
4. Configurer leurs propriétés.
5. Définir un scénario de trafic.
6. Lancer une simulation.
7. Observer les performances du système.
8. Identifier les goulots d'étranglement.
9. Simuler des pannes.
10. Comprendre les causes des problèmes.
11. Modifier l'architecture.
12. Comparer les résultats avant et après modification.
13. Apprendre les concepts techniques concernés.

L'expérience doit être intuitive pour un débutant tout en permettant
aux utilisateurs avancés d'explorer des architectures complexes.

Le produit doit ressembler à un outil d'ingénierie professionnel,
et non à un simple site de cours.

INSPIRATIONS :
- n8n pour l'édition visuelle et les connexions.
- React Flow pour le canvas interactif.
- Linear pour la sobriété de l'interface.
- Grafana pour les tableaux de bord techniques.
- Figma pour la manipulation fluide des éléments.

Ne copie pas exactement ces produits.
Crée une identité propre à SystemLab.

Langue principale : français.
Les noms techniques reconnus peuvent rester en anglais.

==================================================

C'est le cœur de SystemLab.

de code.

Utilise React Flow pour gérer le canvas.

Fonctionnalités obligatoires :

- Ajouter un composant par glisser-déposer.
- Déplacer les composants.
- Sélectionner un composant.
- Sélectionner plusieurs composants.
- Relier les composants.
- Déplacer les connexions.
- Supprimer une connexion.
- Supprimer un composant.
- Dupliquer un composant.
- Copier et coller.

- Ajouter des notes.
- Créer des groupes visuels.

- Sauvegarder les modifications.

Les groupes visuels doivent permettre de regrouper des composants

==================================================
9. ARCHITECTURE DU MOTEUR DE SIMULATION
==================================================

C'est la partie technique la plus importante.

Construis un moteur hybride combinant :

A. Calculs mathématiques.
B. Simulation événementielle.

Sépare le moteur de simulation du code React.

Le moteur doit pouvoir être testé indépendamment de l'interface.

Ne mets pas la logique de calcul directement dans les composants UI.

Architecture logique suggérée :

src/
  app/
  components/
    editor/
    nodes/
    panels/
    simulation/
    charts/
    ui/
  features/
    architectures/
    components-library/
    simulations/
    learning/
  engine/
    graph/
    math/
    events/
    queueing/
    failures/
    metrics/
    diagnostics/
  lib/
    validation/
    persistence/
  stores/
  types/
  tests/

Adapte cette structure à celle du projet existant.

A. MOTEUR MATHÉMATIQUE

Utiliser des calculs déterministes pour estimer :
- Capacités.
- Débits.
- Utilisation des ressources.
- Latences.
- Files d'attente simplifiées.
- Limites de concurrence.
- Coûts estimés.
- Propagation des goulots d'étranglement.

B. MOTEUR ÉVÉNEMENTIEL

Simuler :
- Arrivée des requêtes.
- Déplacement des requêtes dans le graphe.
- Traitement par les composants.
- Files d'attente.
- Délais de traitement.
- Délais réseau.
- Concurrence.
- Saturation.
- Erreurs.
- Timeouts.
- Pannes.
- Reprise des services.
- Retry.
- Circuit Breaker.
- Événements asynchrones.

Utilise une horloge virtuelle et une file d'événements ordonnée
par temps de simulation.

Ne simule pas chaque requête individuelle lorsque le volume rend
cette approche trop coûteuse.

Prévois plusieurs niveaux de précision :

1. Estimation analytique rapide.
2. Simulation événementielle avec échantillonnage.
3. Simulation détaillée pour les scénarios compatibles.

Les résultats doivent préciser le mode utilisé.

C. PROPAGATION DES REQUÊTES

Une requête doit pouvoir traverser plusieurs composants.

Exemple :

Clients
  -> Load Balancer
  -> API Servers
  -> Redis
  -> PostgreSQL

Le moteur doit :
- Respecter les connexions du graphe.
- Calculer les délais de traitement.
- Tenir compte des capacités.
- Simuler les files d'attente.
- Propager les erreurs.
- Calculer les métriques de bout en bout.

Le moteur doit détecter les cycles dans le graphe.

Les cycles ne doivent pas provoquer de boucle infinie.

Une architecture invalide doit recevoir un diagnostic compréhensible.

D. FILES D'ATTENTE

Modéliser au minimum :
- Capacité de service.
- Nombre de workers.
- Temps de service.
- Nombre de requêtes en attente.
- Saturation.
- Temps d'attente.
- Rejets lorsque les limites sont atteintes.

Évite les formules simplistes lorsque leurs hypothèses ne sont
pas satisfaites.

Par exemple, une approximation de file d'attente ne doit pas être
présentée comme fiable lorsque le système est instable.

E. LATENCE

Distinguer :
- Latence réseau.
- Temps de traitement.
- Temps d'attente.
- Latence totale.
- Moyenne.
- p50.
- p95.
- p99.

Les percentiles doivent être calculés à partir de données simulées
appropriées ou d'une approximation explicitement documentée.

Ne calcule pas le p95 en multipliant arbitrairement la moyenne.

F. CAPACITÉ ET SATURATION

Calculer les limites en fonction des paramètres du composant.

Une saturation doit avoir des conséquences cohérentes :
- Augmentation de la file d'attente.
- Augmentation de la latence.
- Rejets.
- Timeouts.
- Propagation de la surcharge.

G. RÉPPLICATION ET CACHE

Implémenter progressivement les modèles de :
- Cache hit et cache miss.
- Politiques de cache.
- Réplication en lecture.
- Réplication en écriture.
- Latence de réplication.
- Capacité des réplicas.

Documenter les hypothèses de chaque modèle.

H. PANNES

Permettre de configurer :
- Début de la panne.
- Durée.
- Composant concerné.
- Indisponibilité complète ou dégradation.
- Temps de récupération.

Observer les conséquences sur les composants dépendants.

I. REPRODUCTIBILITÉ

Permettre de configurer une seed aléatoire.

À paramètres et seed identiques, les résultats doivent être
reproductibles autant que possible.

J. MÉTRIQUES

Produire :
- Débit entrant.
- Débit traité.
- Latence.
- Erreurs.
- Rejets.
- CPU estimé.
- Mémoire estimée.
- Longueur des files.
- Temps d'attente.
- Disponibilité simulée.
- Coût estimé.

Chaque métrique doit avoir une définition claire.

Ne mélange pas les unités.

11. DIAGNOSTICS INTELLIGENTS
==================================================

Créer un moteur de diagnostic basé sur des règles explicites
et sur les métriques produites par le simulateur.

Ne rends pas l'utilisation d'une API d'IA obligatoire pour
obtenir des diagnostics corrects.

Exemples de règles :

- Saturation d'un composant.
- File d'attente qui augmente.
- Dépendance critique sans redondance.
- Base de données trop sollicitée.
- Cache peu efficace.
- Trop de connexions concurrentes.
- Risque de cascade de timeouts.
- Composant isolé.
- Connexion invalide.
- Architecture impossible à simuler correctement.

Chaque diagnostic contient :

- Gravité.
- Composant concerné.
- Métriques justificatives.
- Cause probable.
- Explication pédagogique.
- Solutions possibles.
- Compromis.
- Limites de la recommandation.

Exemple :

"PostgreSQL devient le principal goulot d'étranglement."

Afficher les métriques qui justifient cette conclusion.

Puis proposer plusieurs pistes :
- Optimiser les requêtes.
- Ajouter un cache.
- Augmenter la capacité.
- Introduire des réplicas de lecture.

Préciser les conditions dans lesquelles chaque solution est utile.

Ne recommande pas automatiquement un réplica de lecture pour
résoudre une surcharge principalement liée aux écritures.

17. SÉCURITÉ ET QUALITÉ
==================================================

Même si la première version est locale, adopte de bonnes pratiques.

- Valider les configurations avec Zod.
- Éviter l'exécution de code utilisateur arbitraire.
- Ne pas exécuter de commandes système issues des composants.
- Limiter le nombre de nœuds simulables.
- Limiter la durée maximale d'une simulation.
- Éviter les boucles infinies.
- Prévenir les calculs excessifs.
- Gérer les erreurs proprement.
- Ne jamais exposer de secrets côté client.
- Ne pas faire confiance aux paramètres venant du navigateur.
- Nettoyer les ressources des Web Workers.
- Prévoir des limites de mémoire et de temps.

Les tests de sécurité de la plateforme doivent être simulés dans
le moteur pédagogique.

Ne prétends pas effectuer de véritables audits de sécurité de systèmes
externes.

Ne génère pas de trafic d'attaque vers des services tiers.

==================================================

L'éditeur doit rester fluide même avec plusieurs dizaines de nœuds.

- Éviter les re-renders inutiles.
- Utiliser des sélecteurs Zustand adaptés.
- Séparer le moteur de simulation de React.
- Éviter de recalculer toutes les métriques à chaque frappe.
- Utiliser un Web Worker pour les simulations suffisamment coûteuses.
- Permettre d'arrêter une simulation.
- Afficher les erreurs et les états de chargement.
- Utiliser des types TypeScript stricts.
- Éviter les dépendances inutiles.
- Ne pas utiliser de gros composants monolithiques.

Ne crée pas un fichier unique contenant toute l'application.

Organise le code en modules cohérents.
